## Where it started

Three dogfood recipes ran on the repo, each through a `task`, and CI's engine job runs `bnto check recipes/` and the size budget:

| Recipe        | Does                                                   | Nodes doing the work                                                 |
| ------------- | ------------------------------------------------------ | -------------------------------------------------------------------- |
| `size-budget` | Fails on any file in `apps/web/public` over its budget | `file-list`, `file-collect`, `file-filter`, `file-inspect`, `assert` |
| `grab-bags`   | Fails on `utils`/`helpers`/`hooks` files               | `file-filter`, `assert`                                              |
| `favicons`    | Renders the PNG favicons from `favicon.svg`            | `vector-rasterize`, `image-pad`, `image-resize`, `image-compress`    |

Git hooks stay shell scripts: a hook can't count on a contributor having a built `bnto`.

## How to pick what to dogfood

1. **bnto's own nodes do the work.** A recipe that is only `shell-run` around a command is a slower `task`. Where no node exists yet, a `shell-run` step is fine if it names the gap that will replace it.
2. **It runs in CI,** so it's also an integration test: a node change that breaks it fails the PR.
3. **It fixes real pain or finds a real problem,** not a demo.
4. **It stays off the critical path until it has proven itself.** Release CI keeps its scripts; a recipe runs beside them first.
5. **It never makes its own test inputs.** Fixtures generated by the tool under test hide that tool's bugs.

## What measuring found (October 23, 2026)

- **About 60% of the web's non-WASM assets looked unused.** 1.7 MB of `apps/web/public` (2.9 MB without the WASM bundle) was referenced nowhere: `logos/`, `testimonials/`, `investors/`, `resource-allocation/`, `about/`, `features/` (one card embeds two base64 PNGs, 391 KB), `hero.webp`, `logo.svg`, `footer.svg`, `mascots/sushi-shoyu-alt.svg`. They date from the February UI consolidation (b9b01143), and no homepage plan uses them. **Decided: delete them all** (PR 1).
- **Web-only PRs skipped the size budget.** It runs in the engine job, which `apps/**` changes don't trigger (PR 2 fixes this).
- **Optimizing SVGs isn't worth it.** bnto's own `optimize-svg` over all 39 SVGs saved 1.5% (1.87 MB to 1.84 MB). The WebPs were already made with cwebp.
- **The Rust 400-production-line limit wasn't enforced** (only TypeScript's, through ESLint `max-lines`). One file was over: `bnto-core/src/metadata/node_types.rs` (451). **Decided: split it** (PR 3), then enforce the limit (PR 4). Counting strictly for PR 4 found a second, `bnto/src/tui/mod.rs` (406), which an early `#[cfg(test)] use` had hidden from a "count up to the first `#[cfg(test)]`" rule (PR 3b).
- **Checking a release was manual.** After v0.18.0, crates.io, the GitHub Release and the production deploy were checked by hand (PR 5).
- **Repo recipes are invisible to bnto.** `RecipeCatalog::load` reads only bundled recipes and the user's library, so `bnto list` and `bnto tui` can't see them (PRs 7a-7d).
- **Existing issues found along the way:** telemetry sends custom recipe names and run-by-path file paths as `slug` (PR 6a), and `test_list_command` reads the developer's real `~/.bnto` (PR 6b).

## Not dogfooded, on purpose

- **Build and codegen orchestration** (`wasm:codegen`, `nodes:codegen`, `readme:generate`): it runs programs in order, which is Task's job. A related non-bnto fix: re-format `bnto_wasm.js` inside `wasm:copy`, so codegen stops leaving a manual prettier step.
- **Git hooks,** per the rule above.
- **Test fixture generation,** which is circular (rule 5).
- **Image and SVG optimization of the site,** which measured negligible savings.

## Project recipes (PRs 7a-7d)

When bnto runs inside a git repo, it also loads `*.bnto.json` from `<git root>/.bnto/recipes/`. That folder name, like `.github/workflows`, means a repo's unrelated `recipes/` folder is never picked up. bnto's own dogfood recipes move there in 7d. The full design goes in a decision record (`.claude/decisions/project-recipes.md`), reviewed by `/security-engineer`, before 7a.

- **A project recipe never overrides a bundled or library slug.** Otherwise a cloned repo could shadow `compress-images` with `file-delete` steps, and running it inside that repo would delete files with no prompt. A colliding project recipe is skipped; `bnto list`, `doctor` and a run of that slug say so.
- **Every project recipe asks consent on its first run,** even without shell steps (hash-approved like library shell recipes). It came from a repo the user cloned, not from their own library. Running a recipe by file path keeps today's shell-only rule.
- **Discovery** walks up from the current directory to the first `.git` dir or file (worktrees and submodules), spawning no `git` process. It happens in `main.rs` and at TUI launch, not inside `RecipeCatalog::load`, so tests that load the catalog from inside this repo don't pick up its recipes.
- **CI and Task keep running dogfood recipes by path:** a slug would need consent, and CI can't answer a prompt.

## Product gaps this surfaces (PRs 8-10)

Each is a generic building block, not a dogfood special case. Each PR swaps its recipe's `shell-run` step for the node.

| Gap            | Replaces                 | Shape                                                                                                                                                                             |
| -------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Line count     | awk in `rust-file-size`  | `file-inspect` attaches `line_count` for text files, with a way to skip top-level `#[cfg(test)] mod` blocks wherever they sit (counting up to the first one misses code after it) |
| Content search | grep in `unused-assets`  | Keep or drop files whose text contains a pattern: a new node or a `file-filter` content criterion, decided per `generic-building-block-nodes.md`                                  |
| HTTP request   | curl in `release-verify` | The `http-request` node the architecture anticipates; its own design doc first (allowlist, timeouts, consent)                                                                     |
