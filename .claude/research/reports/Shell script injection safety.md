# Ship literal scripts, but seal the environment

_Research report, 2026-10-20. Synthesized from the four note files in `.claude/research/research_notes/Shell script injection safety/`. Facts about bnto's code are cited as "(bnto source)". They come from the coordinator's verified context, plus a few spot checks made while writing this report, which give the file path._

## Executive summary

**The proposed `script` param is the right design and matches the industry's safest pattern.** The param runs a literal, never-templated script as `<shell> -c <script> <name> <args...>`, with values arriving only as `$1..$N`. Every mature tool that was burned by shell injection arrived at the same fix: keep the author's code static and send runtime values out of band. GitHub Actions uses env vars, Jenkins uses literal single-quoted strings plus `withEnv`, and Airflow uses `env=`. Windmill, Raycast, Alfred and Automator all pass values as positional args ([GitHub](https://docs.github.com/en/actions/reference/security/secure-use), [Jenkins](https://www.jenkins.io/doc/book/pipeline/jenkinsfile/), [Airflow](https://airflow.apache.org/docs/apache-airflow-providers-standard/stable/operators/bash.html), [Windmill](https://windmill.dev/docs/getting_started/scripts_quickstart/bash), [Alfred](https://www.alfredapp.com/help/workflows/actions/run-script/)). Rejecting `{{` outright goes further than every peer surveyed, all of which permit the dangerous form and rely on documentation or linters.

**The real gaps are elsewhere.** First, the shell can run code from the **environment** before line 1 of the script. On macOS, `SHELLOPTS=xtrace` plus `PS4='$(cmd)'` executes code under bash _and_ `/bin/sh`. `BASH_FUNC_ls%%` silently replaces any command name. `BASH_ENV` and `$ZDOTDIR/.zshenv` source arbitrary files ([GNU Bash](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html), [zsh](https://zsh.sourceforge.io/Doc/Release/Files.html)). bnto passes the full parent environment and strips only seven names from the recipe's `env`. Recipe `env` _values_ are templated, so a templated value written into `PS4` or `BASH_ENV` turns data back into code even when the script is literal (bnto source). Second, the **template check must run on the raw definition**: the executor resolves `{{...}}` in every param before the processor sees it, so a check inside the processor comes too late (bnto source). Third, the existing `command` path already allows `python3 -c "print('{{item.name}}')"`. That is the exact template-before-parse bug behind Budibase CVE-2026-25044 and Airflow's two example-DAG CVEs, one of which is in CISA's KEV catalog ([CVE-2026-25044](https://cveawg.mitre.org/api/cve/CVE-2026-25044), [GHSA-rvmq-4x66-q7j3](https://github.com/advisories/GHSA-rvmq-4x66-q7j3)).

**Required before shipping `script`:**

1. Validate the raw definition, and exempt `script` from template resolution.
2. Run script mode with `env_clear()` plus an allowlist, and reject shell-startup variable names in the recipe's `env`.
3. Resolve shells to absolute paths and harden them (`bash -p`, `zsh -f`, a fixed `$0`).
4. Enforce enum membership in the engine. A spot check found that `--param` accepts any string for an enum field.
5. Ship the bundled keep-awake script ShellCheck-clean, quoting every value and validating it with `case`.

Closing the `-c`/`-e` interpreter gap, adding argument-injection guards, and the PowerShell channel come next.

First, **shell access survives only in single-tenant or self-hosted tools, and there it is increasingly off by default**: n8n 2.0 turned Execute Command off, Huginn ships it disabled, and Zapier and Make never offered it ([n8n 2.0](https://docs.n8n.io/2-0-breaking-changes), [Huginn](https://codeclimate.com/github/cantino/huginn/.env.example/source)). bnto's per-recipe consent hash is a finer-grained version of the same gate. ## Five practices every credible source converges on

**Practice 1: data never touches the parser.** OWASP's top defense is to avoid shells. When a command is unavoidable, OWASP calls for "structured mechanisms that automatically enforce the separation between data and command", and it ranks escaping as weaker ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)). POSIX defines exactly such a mechanism for shells: `sh -c command_string command_name args...` sets `$0` from `command_name` and `$1…` from the remaining operands ([POSIX](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/sh.html)). ShellCheck SC2156 prescribes `sh -c '...' shell "$value"` over splicing, because splicing "can break the script and allow arbitrary code execution exploits" ([SC2156](https://www.shellcheck.net/wiki/SC2156)). GitHub explains why the out-of-band channel works: the value "doesn't interact with the script generation process" ([GitHub](https://docs.github.com/en/actions/reference/security/secure-use)). The research notes confirmed this with a local test: a value of `$(echo INJECTED); rm -rf x \`id\``passed as`$1` printed literally.

**Practice 2: indirection only works if nothing re-templates it.** CodeQL flags `echo '${{ env.BODY }}'` as still vulnerable even though BODY came from an env var, and zizmor says "you **should not** use `${{ env.VARNAME }}`" ([CodeQL](https://codeql.github.com/codeql-query-help/actions/actions-code-injection-critical/), [zizmor](https://docs.zizmor.sh/audits/)). The guarantee therefore has to be structural, not advisory. The Ultralytics compromise slipped past zizmor because the injection sat inside a composite action that the linter did not yet audit ([yossarian](https://blog.yossarian.net/2024/12/06/zizmor-ultralytics-injection)). The same attack shows that character filtering fails: the branch name `$({curl,-sSfL,...}${IFS}|${IFS}bash)` contains no spaces at all.

**Practice 3: allowlist, don't denylist.** CWE-88 says "do not rely exclusively on looking for malicious or malformed inputs", and OWASP says commands "must be validated against a list of allowed commands". Arguments get allowlist regexes with length limits ([CWE-88](https://cwe.mitre.org/data/definitions/88.html), [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)). GTFOBins catalogs how many ordinary binaries can spawn shells or run code ([GTFOBins](https://gtfobins.github.io/)). n8n's run of denylist-sanitizer and in-process-sandbox escapes is a live demonstration. CVE-2026-25049 bypassed a `Set.has()` property denylist simply by passing an array ([Endor](https://www.endorlabs.com/learn/cve-2026-25049-n8n-rce)).

**Practice 4: argument injection survives "no shell".** OWASP states that "every OS Command Injection is also an Argument Injection". It recommends `--` "for commands that support it", and warns that for curl `--` "does not prevent additional transfers" ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)). CWE-88's observed examples include PHPMailer's `-X` sendmail switch reaching RCE (CVE-2016-10033) ([CWE-88](https://cwe.mitre.org/data/definitions/88.html)). Home Assistant's 2026 ffmpeg bug was exactly this: a single argv element, no shell, and still a root-equivalent token leak through ffmpeg pseudo-protocols ([elttam](https://elttam.com/blog/your-house-has-an-ffmpeg-problem)).

**Practice 5: the author is trusted, the data is not, and consent gates authorship.** Home Assistant requires the program name to be "literally provided". Airflow names `dag_run.conf` as the untrusted input. n8n and Huginn gate the whole capability on trusting "everyone using your installation" ([HA](https://www.home-assistant.io/integrations/shell_command/), [Airflow](https://airflow.apache.org/docs/apache-airflow-providers-standard/stable/operators/bash.html), [Huginn](https://github.com/huginn/huginn/blob/master/app/models/agents/shell_command_agent.rb)). Coder's CVE-2026-44454 shows how this breaks: a deep link "silently provisioned a workspace … with no explicit user confirmation", which turned an injection into "a one-click attack" ([CVE-2026-44454](https://cveawg.mitre.org/api/cve/CVE-2026-44454)).

## bnto today: a strong argv core with three leaks

### What bnto already gets right

**The argv core is stronger than most peers.** Each `{{...}}` resolves into one element of a JSON args array and is never re-split (bnto source). That is stricter than Home Assistant, which renders the whole argument string and then `shlex.split`s it, so a value containing spaces becomes several arguments ([services.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/shell_command/services.py)). It is also stricter than Node-RED, which appends the payload to a bash string ([90-exec.js](https://raw.githubusercontent.com/node-red/node-red/master/packages/node_modules/%40node-red/nodes/core/function/90-exec.js)). bnto's model is GitHub's "preferred mitigation #1": the value "is not used to generate a shell script" ([GitHub](https://docs.github.com/en/actions/reference/security/secure-use)).

Several other controls are already in place:

- **Env names are never templated**, which avoids the attacker-chosen-variable-name problem that zizmor's `github-env` audit targets ([zizmor](https://docs.zizmor.sh/audits/)).
- **The recipe's `env` cannot override `PATH`, `LD_PRELOAD`, or `DYLD_*`.**
- **Processes are reaped by process group or Job Object** (bnto source).
- **The toolchain is past both BatBadBut fixes.** MSRV 1.88 is newer than 1.77.2 (CVE-2024-24576) and 1.81.0 (CVE-2024-43402) (bnto source; [Rust](https://blog.rust-lang.org/2024/04/09/cve-2024-24576/), [GHSA-2xg3](https://github.com/rust-lang/rust/security/advisories/GHSA-2xg3-7mm6-98jj)).
- **URL-mode inputs are scheme-checked.** A spot check of `engine/crates/bnto/src/input.rs` shows they must start with `http://` or `https://` before being appended to the args. A URL input therefore cannot begin with `-` (bnto source).

### Leak 1: templated data into interpreter code is allowed today

`python3 -c`, `node -e`, `perl -e` and `osascript -e` pass the denylist. The executor resolves templates into those code strings, so `python3 -c "print('{{item.name}}')"` makes a CSV cell or filename part of the program (bnto source). This is the Budibase, Airflow and Windmill bug class: a value is interpolated into source text that a parser then executes ([CVE-2026-25044](https://cveawg.mitre.org/api/cve/CVE-2026-25044), [Airflow](https://airflow.apache.org/docs/apache-airflow-providers-standard/stable/operators/bash.html), [Windmill GHSA](https://github.com/windmill-labs/windmill/security/advisories/GHSA-8q8j-mm3g-5c2q)). **Once `script` ships, bnto will forbid templating into `sh` code while still permitting it into Python code.** That inconsistency is hard to defend. Ryan's personal keep-awake recipe already uses the safe form: a literal `python3 -c` program that reads `sys.argv[1..4]` (seen in `~/.bnto/recipes/keep-awake.bnto.json`).

### Leak 2: the shell denylist is a nudge, not a boundary

Any GTFOBins-style wrapper or interpreter reaches a shell, for example `python3 -c 'import os; os.system(...)'` ([GTFOBins](https://gtfobins.github.io/)). Real author trust comes from the consent hash, not from the denylist. The denylist does have one job worth keeping, covered under recommendation 10.

### Leak 3: enum values are not checked against their options

A spot check found that `apply_node_field_in_nodes` (`engine/crates/bnto/src/input.rs`) writes any `--param` string into an enum field's default. `collect_field_values` (`engine/crates/bnto-core/src/executor/resolve.rs`) then lets overrides win without consulting `options` (bnto source). The bundled `download-video` recipe deliberately uses option-shaped enum values such as `--embed-thumbnail` and `--sponsorblock-remove=default`, which are placed directly in yt-dlp's argv. The planned keep-awake script will pass `display` straight to `caffeinate` as a flag. In both cases **the enum is the only allowlist standing between a value and an option slot**, and it is not enforced in the paths checked. Today the person typing `--param` is the local user, so the immediate risk is low. However, this is OWASP's "layer 2" allowlist validation, and it becomes load-bearing as soon as values arrive from anywhere else.

## The `script` proposal: correct core, gaps at the edges

**Strengths.** The proposal is the POSIX- and SC2156-endorsed form ([POSIX](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/sh.html), [SC2156](https://www.shellcheck.net/wiki/SC2156)). It holds up on four further points:

- **Rejecting `{{` is stricter than any peer.** It makes the vulnerable form unrepresentable instead of something linters have to chase.
- **The shell choice is an allowlist.** The five named shells are the "list of allowed commands" OWASP asks for.
- **A fixed `<name>` avoids the `$0` shift.** POSIX takes `$0` from the first operand when `command_name` is omitted, which would shift every value by one. SC2156 also advises against putting data in `$0`.
- **The static script makes consent meaningful.** Because the script text never changes, the SHA-256 consent pin covers exactly the code that runs.

Positional args are also **at least as strong as env vars**: they don't leak into grandchildren's environments, and they can't collide with `PATH` or `IFS`.

### Gap A: where the `{{` check lives

The executor resolves templates in _all_ params before the processor runs (bnto source). If the "reject `{{`" check sits in the shell-command processor, it inspects an already-resolved script, and the spliced data passes the check. The check must run on the **raw definition** at load or validation time, and the executor must **skip resolution for `script`**, plus `shell` and the `$0` name if those become params. This is the CodeQL `${{ env.BODY }}` lesson applied to bnto's own pipeline: a safe channel is useless if an earlier stage re-inlines the value ([CodeQL](https://codeql.github.com/codeql-query-help/actions/actions-code-injection-critical/)).

### Gap B: the environment runs code before the script does

The research notes verified these with primary docs and local tests (macOS: bash 3.2, `/bin/sh` = bash-as-sh, dash, ksh93, zsh 5.9):

bnto strips none of these names from the recipe's `env`. Because env **values** are templated, a recipe containing `"env": {"SHELLOPTS": "xtrace", "PS4": "{{item.name}}"}` reopens template-into-code through a side door. A consent reviewer reading the script would see nothing wrong. Separately, the inherited parent environment carries any `BASH_ENV` or `BASH_FUNC_*` the user's own shell exported. Those are not attacker-controlled, but they make runs non-reproducible. **Flags alone do not cover `sh`**, because macOS `/bin/sh` honored `BASH_FUNC_*` and `SHELLOPTS`/`PS4` in the local tests. The notes did not test whether `/bin/sh -p` suppresses them. That leaves `env_clear()` as the primary control and flags as belt-and-braces.

### Gap C: script-author hygiene stays unenforced

Local tests in the notes showed two failure modes. An unquoted `$1` word-splits and globs: `'a * b'` expanded to the filesystem root listing. `eval "echo $1"` executes the injected command. Nested sinks re-introduce injection exactly the way splicing does: `sh -c "...$1..."`, `osascript -e "...$1..."`, `python3 -c "...$1..."`, `xargs sh -c`, `find -exec sh -c`. The engine cannot see inside these. GitHub, Kestra and Windmill all leave this to the author, and Raycast's own example interpolates `$1` unquoted into a URL ([Raycast](https://raw.githubusercontent.com/raycast/script-commands/master/documentation/ARGUMENTS.md)).

### Gap D: argument injection is unchanged

A quoted `"$1"` that begins with `-` is still an option to whatever command receives it ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)). `--` helps only for getopt-style programs, so bnto cannot enforce it generically.

### Gap E: the Windows channel needs care

PowerShell `-Command <string>` appends every following argument to the code: "all arguments following it are interpreted as part of the command to execute" ([about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh)). Passing values as trailing args would therefore recreate the injection. `-CommandWithArgs` populates `$args` but exists only in pwsh 7.4 and later. Windows PowerShell 5.1 has no equivalent ([about_PowerShell_exe 5.1](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1)). Profiles load unless `-NoProfile` is passed ([about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh)). The env-var plan is correct, and it is the only channel that works on both 5.1 and 7.x without touching the Windows command line.

### Trade-offs behind the top items

**`env_clear()` vs extending the strip list.** A denylist has to anticipate every startup hook in five shells plus each interpreter. The notes also flag `PYTHONSTARTUP`, `NODE_OPTIONS` and `PERL5OPT` but did not source them, which shows how open-ended that list gets. An allowlist fails closed. The cost is that a script relying on the user's `SSH_AUTH_SOCK` or an API-key variable breaks until the recipe declares it. Script mode is new, so it has no backward-compatibility cost, which makes it the right place to start. For the existing `command` mode, keep inheriting the parent env for now, since yt-dlp may need proxy variables. Do add the startup-variable names to the recipe-`env` strip list there, because a `python3 -c` program that shells out would honor them.

**`bash -p` and `zsh -f`.** With uid equal to euid, `bash -p` acts as a pure "ignore env imports" switch. It drops `BASH_ENV`, `ENV`, inherited functions and `SHELLOPTS`, and in bash 4+ also `BASHOPTS`, `CDPATH` and `GLOBIGNORE` ([Set builtin](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)). The only loss is scripts that expected exported functions, which bnto does not want anyway. `zsh -f` skips the user's `.zshenv`/`.zshrc`. Authors who rely on `.zshenv` for Homebrew `PATH` additions lose nothing, because bnto passes the parent `PATH` explicitly. The gain is determinism: a script that runs the same on every machine.

**Positional args vs named env vars.** Keyboard Maestro and Airflow show that named env values (`"$BNTO_FIELD_action"`) read better than `$3` ([KM](https://wiki.keyboardmaestro.com/action/Execute_a_Shell_Script), [Airflow](https://airflow.apache.org/docs/apache-airflow-providers-standard/stable/operators/bash.html)). Positional args are the better POSIX default because they cannot collide with real variables. If named access is added later, prefix the names, never let data choose them, and pass them only through the cleared environment.

### Open uncertainties

The notes did not test five things:

- whether Linux bash 5.x suppresses `BASH_FUNC_*` import in posix mode (Debian and Ubuntu `/bin/sh` is dash, which does not import functions);
- whether `/bin/sh -p` on macOS blocks `SHELLOPTS`/`PS4`;
- whether `PSModulePath` injection affects a `-NoProfile` child;
- the per-interpreter argv conventions recommendation 3 relies on (`sys.argv`, `process.argv`, `@ARGV`, osascript `run argv`), which are inference rather than cited docs;
- the ksh93 `FPATH` hijack, which rests on a local test alone.

The enum-membership finding comes from a spot check of two code paths. Confirm that no other validation layer exists before writing the fix.

## Conclusion

The design question has quietly shifted. The proposal already solves the problem it set out to solve, values becoming shell syntax, and it does so more strictly than GitHub, Jenkins, Airflow or Home Assistant. What remains is that **the shell has inputs other than its script**: the environment it inherits, the env values bnto templates into it, and the startup files it reads. Each is a code channel that bypasses a literal script. On macOS, `/bin/sh` is itself bash and honors two of them. Sealing those channels with a cleared environment, absolute shell paths and `-p`/`-f` is what turns "the script is the only code" from a convention into an invariant.

The second shift is that shipping `script` exposes the inconsistency in the existing `command` path. Once templating into `sh -c` is forbidden, templating into `python3 -c` becomes the obvious next Budibase. The bundled keep-awake recipe is the first thing users will copy, so like Airflow's example DAGs it sets the security bar for every recipe that follows.
