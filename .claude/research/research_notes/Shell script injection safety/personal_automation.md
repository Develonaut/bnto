# Personal / home automation tools: shell commands with dynamic values and injection defenses

Research date: 2026-10-20. Scope: Home Assistant (`shell_command`, `command_line`), Node-RED `exec`, Apple Automator and Shortcuts "Run Shell Script", Alfred Run Script, Raycast Script Commands, Keyboard Maestro "Execute Shell Script". Huginn is excluded because another researcher covers it.

## Home Assistant `shell_command` and `command_line`: what is the "more secure environment" and how does it work?

### Takeaway

Home Assistant uses two code paths. A command with no template runs through a shell (`create_subprocess_shell`). If a template changes the arguments, HA takes the literal program name, renders the argument string, splits it with `shlex.split`, and runs it with `create_subprocess_exec`, so no shell is involved. The program name can never come from a template. This prevents shell injection. It does not prevent argument injection, because the rendered value is split after substitution, so a value with spaces or quotes can become extra argv entries. I found no CVE against `shell_command` or `command_line` themselves. Real HA incidents in this area are argument injection into a binary called without a shell (ffmpeg) and command injection in go2rtc.

### Cited Findings

- Docs, verbatim: "The commands can be dynamic, using templates to insert values for arguments." Also: "When using templates, shell_command runs in a more secure environment that doesn't allow any shell helpers, such as automatically expanding the home directory character (`~`), using pipe symbols (`|`) to run multiple commands, or operators redirecting output (such as `>` and `>>`)." — [HA docs source, shell_command.markdown](https://raw.githubusercontent.com/home-assistant/home-assistant.io/current/source/_integrations/shell_command.markdown); rendered page: [home-assistant.io/integrations/shell_command](https://www.home-assistant.io/integrations/shell_command/)
- Docs: "only content after the first space can be generated by a template. This means the command name itself cannot be generated by a template, but it must be literally provided." — [HA docs source](https://raw.githubusercontent.com/home-assistant/home-assistant.io/current/source/_integrations/shell_command.markdown)
- Docs: "the shell command process is terminated after 60 seconds. There is no option to alter this behavior. This is by design because Home Assistant is not intended to manage long-running external processes." The response is a dict with `stdout`, `stderr` and `returncode`. — [HA docs source](https://raw.githubusercontent.com/home-assistant/home-assistant.io/current/source/_integrations/shell_command.markdown); [shell_command page](https://www.home-assistant.io/integrations/shell_command/)
- Implementation in `services.py`:
  - The command is split with `prog, args = cmd.split(" ", 1)` and only `args` is compiled as a template (`template.Template(str(args), hass)`).
  - If `rendered_args == args`, the comment is `# No template used. default behavior` and the command runs via `asyncio.create_subprocess_shell(...)`.
  - Otherwise the comments read `# Template used. Break into list and use create_subprocess_exec` and `# (which uses shell=False) for security`, followed by `shlexed_cmd = [prog, *shlex.split(rendered_args)]` and `asyncio.create_subprocess_exec(...)`.
  - The timeout is `COMMAND_TIMEOUT = 60`.
  - Source: [home-assistant/core shell_command/services.py (dev)](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/shell_command/services.py)
- `command_line` integration docs follow the same model. "While `command` accepts a template, only the arguments can be generated by a template." "When using templates, the command runs in a more secure environment that doesn't allow any shell helpers." Commands run "in the `homeassistant` container context". The default `command_timeout` is 15 s, and when a command exits non-zero or times out, "the result is only logged". The docs recommend wrapping commands in single quotes (doubling any internal single quote) because this "ensures all characters can be used in the command and reduces the risk of unintentional escaping". — [home-assistant.io/integrations/command_line](https://www.home-assistant.io/integrations/command_line/)
- The shell_command page has no dedicated security warning. Its only "Important" callout is about hidden dot-directories such as `.ssh`. — [shell_command page](https://www.home-assistant.io/integrations/shell_command/)
- Incident: argument injection without a shell, in the Wyoming `announce` service. Attacker-influenced `media_id` went as a single argv element to ffmpeg via `asyncio.create_subprocess_exec`. ffmpeg pseudo-protocols (`concat:`, `subfile:`, `file:`) were not blocked, which allowed arbitrary file read including `/proc/self/environ`. That leaked `SUPERVISOR_TOKEN`, which the author says leads to "command execution as root on the host".
  - Tested on Core 2026.5.4; fixed in 2026.6.2 by adding `-protocol_whitelist http,https,file,tcp,tls` before `-i`.
  - No CVE was assigned and the report was closed N/A, though the issue was fixed. Blog dated 2026-07-29.
  - Source: [elttam, "your house has an ffmpeg problem"](https://elttam.com/blog/your-house-has-an-ffmpeg-problem)
- Incident: ZDI-26-560 (Pwn2Own), a command injection in go2rtc on Home Assistant Green. "The issue results from the lack of proper validation of a user-supplied string before using it to execute a system call." It allows code execution as root. Fixed in go2rtc v1.9.14 and Home Assistant. Reported 2025-11-05, published 2026-08-12, no CVE listed. — [ZDI-26-560](https://www.zerodayinitiative.com/advisories/ZDI-26-560/)
- Related ecosystem CVEs (not the core shell integrations):
  - CVE-2026-53455: shell command injection through Git username/token in Blueprint Studio before 2.5.2. — [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-53455/)
  - CVE-2026-40602 / GHSA-33qf-q99x-wpm8: unsandboxed Jinja2 rendering in hass-cli leads to local code execution; fixed in 1.0.0. — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-40602)

### Inferences

- HA's protection is "no shell when templated", not "values are separate argv". Because the template is rendered into one string and then `shlex.split`, a value containing spaces becomes several arguments. A value containing quotes changes how the string tokenizes and can raise a `shlex` error on unbalanced quotes. So templated values can still inject extra options or arguments into a fixed binary. bnto's current design is stricter: it substitutes into individual elements of a JSON args array, so one value maps to exactly one argv element and is never re-split.
- HA detects "template used" by comparing the rendered output with the source. A command that contains no template markers falls back to a full shell. This is an implicit mode switch based on content, not an explicit setting. An explicit flag, as bnto is considering, is easier to reason about.
- HA never allows templating the program name. This parallels bnto keeping the `sh -c` script literal: the code part stays static and only data varies.
- The ffmpeg incident shows that dropping the shell is not enough when the target binary interprets its own arguments (URLs, protocols, `-` prefixed options). The same applies to bnto's bare-binary mode, and to `$1` inside a literal `sh -c` script if the script passes `$1` to a tool such as ffmpeg, curl or git.

### Gaps

- I found no GHSA or CVE for `shell_command` or `command_line` in the home-assistant/core advisory list (searched; none surfaced). I could not fetch the full advisories page to confirm there are none.
- I did not find when the template-to-exec behaviour was introduced (the PR or version).

## Node-RED `exec` node: exec vs spawn, how msg.payload reaches the command, warnings, CVEs

### Takeaway

In both modes, Node-RED builds a command string and appends `msg.payload` to it. Exec mode (the default) passes that string to a shell (`/bin/bash` on Linux when present) with no escaping, so it is directly injectable. Spawn mode splits the string with a regex and runs it without a shell on POSIX, but forces `shell: true` on Windows. Even on POSIX the payload is re-tokenized, so argument injection is still possible. The help text has no security warning. The core node cannot send the payload on stdin; maintainers discussed that option in 2024. I found no CVE against the core exec node.

### Cited Findings

- Help text: exec mode "By default uses the exec system call which calls the command, waits for it to complete, and then returns the output". Spawn mode "returns the output from stdout and stderr as the command runs, usually one line at a time." `msg.payload` "if configured to do so, will be appended to the executed command." The only quoting guidance is "Commands or parameters with spaces should be enclosed in quotes." There is no security or escaping warning. — [90-exec.html help](https://raw.githubusercontent.com/node-red/node-red/master/packages/node_modules/%40node-red/nodes/locales/en-US/function/90-exec.html)
- Source, exec mode: `var arg = node.cmd; arg += " " + value;` then `exec(arg, node.execOpt, ...)`. `execOpt` sets `shell: '/bin/bash'` on Linux if it exists. No escaping is applied. — [90-exec.js](https://raw.githubusercontent.com/node-red/node-red/master/packages/node_modules/%40node-red/nodes/core/function/90-exec.js)
- Source, spawn mode:
  - The payload is concatenated the same way, then tokenized with `arg.match(/(?:[^\s"]+|"[^"]*")+/g)` and outer double quotes are stripped.
  - On Windows, `opts = { ...node.spawnOpt, shell: true }` and `spawn([cmd].concat(arg).join(" "), opts)` rejoins everything into a shell string. Elsewhere it calls `spawn(cmd, arg, opts)` with no shell.
  - Single quotes and escaped quotes are not handled.
  - Source: [90-exec.js](https://raw.githubusercontent.com/node-red/node-red/master/packages/node_modules/%40node-red/nodes/core/function/90-exec.js)
- Forum, 2024-09-13: the core exec node does not pipe `msg.payload` to stdin.
  - dceejay (Node-RED maintainer) proposed a dropdown, "append msg.xxx as [parameter]/[stdin]", and noted "there is the daemon node for longer running processes that does accept stdin".
  - jbudd noted that scripts passed on the command line must be single-quoted "and thus may not contain single quotes".
  - Injection was not discussed in the thread.
  - Source: [discourse.nodered.org thread 90931](https://discourse.nodered.org/t/exec-node-piping-payload-to-stdin-for-commands/90931)
- FlowFuse's exec guide notes that glob `*` "will not be expanded in the way a user might expect", meaning shell semantics vary with the mode. — [FlowFuse exec docs](https://flowfuse.com/node-red/core-nodes/exec)
- CVE search: no CVE for the core exec node surfaced. The closest results are vendor products that bundle Node-RED:
  - CVE-2026-79698: command injection in Advantech WISE-6610 `nodered_lib_apply`, fixed in 1.2.4_20260821. — [Lutra fieldguide](https://fieldguide.lutrasecurity.com/CVE-2026-79698/)
  - CVE-2023-50203: D-Link G416 Node-RED-related command injection. — [stack.watch](https://stack.watch/vuln/CVE-2023-50203/)

### Inferences

- The Node-RED project appears to treat the exec node as a trusted-operator tool: whoever builds the flow owns the risk. The danger comes from the default (shell string plus raw append) combined with no warning. This is the anti-pattern bnto already avoids.
- Spawn mode on Windows shows how a "no shell" mode can quietly turn back into a shell on one platform. If bnto adds `sh -c`, it should state the behaviour per platform explicitly (`sh` does not exist natively on Windows) and never fall back to `cmd.exe`.

### Gaps

- I did not check GHSA entries for popular contrib exec-style nodes (for example node-red-node-daemon or node-red-contrib-bigexec). None surfaced in search.
- I did not check the "Securing Node-RED" docs page for an exec-specific warning.

## Apple Automator and Shortcuts "Run Shell Script": the "Pass Input: to stdin / as arguments" options

### Takeaway

Automator's Run Shell Script offers "Pass input" as stdin or as shell arguments (`$@`). This has been documented since at least 2007. Values arrive as data on the stdin stream or as positional parameters, never by text substitution into the script. Shortcuts on macOS carries the same action, but I could not retrieve Apple's current wording for it. Community reports confirm Shortcuts also lets you insert variables directly into the script text (right-click, insert variable), and that path is injectable.

### Cited Findings

- Apple developer docs (Automator Concepts, "Updated: 2007-12-11"): "The 'Pass input' pop-up menu lets you choose input in the form of standard input (`stdin`) or as shell arguments." Also: "input is piped into the action via standard input (or passed as command-line arguments) and piped out of it via standard output." Also: "Input to the script is implicitly standard input; you handle it (usually) as lines." The Shell pop-up allows csh, zsh, Python or Perl. — [Apple, Creating Shell Script Actions](https://developer.apple.com/library/mac/documentation/AppleApplications/Conceptual/AutomatorConcepts/Articles/ShellScriptActions.html)
- Apple Community: with "as arguments", input lands in `$@`, and stacking several "Get Value of Variable" actions puts all of them in `$@` as a list. — [discussions.apple.com/thread/1657773](https://discussions.apple.com/thread/1657773)
- Shortcuts community: a user "didn't know that you could insert a variable or the clipboard into the run shell script command, by right-clicking on it". In Shortcuts, inline variable interpolation into the script body is possible alongside Pass Input. — [talk.automators.fm thread](https://talk.automators.fm/t/passing-command-line-arguments-to-shortcut-from-clipboard/14426)

### Inferences

- Apple's long-standing design passes data out-of-band (stdin or `$@`) to a script body the user writes by hand. This is the same shape as bnto's proposed `sh -c '<literal>' name "$@"`. Shortcuts later added inline interpolation into the script, which brings back the injection risk.

### Gaps

- I could not fetch the support.apple.com Shortcuts page for Run Shell Script; the guide page returned only navigation. I could not confirm with a source Apple's current wording for "Pass Input", the "Run as Administrator" option, or the "Allow Running Scripts" setting in Shortcuts > Settings > Advanced. Treat those details as unverified.
- I found no Apple documentation explaining why the stdin and arguments options exist (for example, a security rationale). The 2007 doc frames them only as I/O plumbing.

## Alfred workflows: Run Script "with input as argv" vs "{query}"

### Takeaway

Alfred's own help recommends argv over `{query}` substitution "as you don't have to worry about correctly escaping the inputted query." `{query}` splices text into the script body and depends on per-character escaping checkboxes. Third-party Alfred libraries that build shell strings have had command-injection advisories.

### Cited Findings

- Alfred help: "The input can be passed in as argv or you can replace {query} with the script." Also: "It's recommended that you use argv, as you don't have to worry about correctly escaping the inputted query." The default script includes "the escaping options if using {query}." — [alfredapp.com Run Script help](https://www.alfredapp.com/help/workflows/actions/run-script/)
- Snyk SNYK-JS-ALFREDWORKFLOWNODEJS-608975: alfred-workflow-nodejs allows command injection "by using a semicolon char in any of the key values". No fixed version exists. — [Snyk](https://snyk.io/vuln/SNYK-JS-ALFREDWORKFLOWNODEJS-608975)

### Inferences

- Alfred is the clearest vendor statement in this group. It still supports `{query}` substitution for legacy reasons and relies on escaping as the mitigation, but it explicitly steers users to argv. This matches the bnto proposal: never template the script, pass values positionally.

### Gaps

- The fetched help page did not list the individual escaping checkboxes. From memory they are spaces, backquotes, double quotes, brackets, semicolons, dollars and backslashes, but this is unverified and should not be cited without confirmation.
- I did not find when Alfred introduced argv mode or changed its default (Alfred 3 or 4 era).

## Raycast Script Commands: how arguments are passed

### Takeaway

Raycast passes up to three user-entered arguments as positional parameters (`$1`, `$2`, `$3`) to a script file the user owns. The only encoding option is `percentEncoded`, which is for URLs. The docs say nothing about shell escaping. Their only quality gate is that community scripts must pass ShellCheck.

### Cited Findings

- Arguments are declared with `@raycast.argument1..3` metadata. The fields are:
  - `type` (`text`, `password`, `dropdown`)
  - `placeholder`
  - `optional`
  - `percentEncoded` (Raycast percent-encodes the value, which is useful when passing it into a URL query)
  - `data` (dropdown options)
  - `secure` (deprecated in favour of `password`)
  - The example script uses `$1` and `$2`: `open "https://www.google.com/search?q=flights%20from%20$1%20to%20$2"`.
  - Source: [raycast/script-commands ARGUMENTS.md](https://raw.githubusercontent.com/raycast/script-commands/master/documentation/ARGUMENTS.md)
- README: argument support requires Raycast 1.2.0 or later. "All scripts uploaded to GitHub will need to have been run through ShellCheck." There is no section on argument escaping or untrusted input. — [raycast/script-commands README](https://github.com/raycast/script-commands/blob/master/README.md)

### Inferences

- Raycast's model is "script body is a file, values are argv". It has no mechanism for templating values into the script at all, so the injection surface is limited to how the script itself uses `$1`. ShellCheck enforces quoting hygiene such as SC2086 for unquoted variables. bnto could recommend ShellCheck-style quoting (`"$1"`) in its docs for literal scripts.
- Raycast's own example interpolates `$1` unquoted into a URL string. Even official examples get quoting hygiene wrong, so docs and examples for bnto's feature should show `"$1"`.

### Gaps

- I found no Raycast security advisories related to script commands.

## Keyboard Maestro "Execute Shell Script": variables as environment variables

### Takeaway

Keyboard Maestro passes macro variables to scripts as environment variables (`KMVAR_<Name>`), and since v8 can also send chosen input on stdin. Its wiki documents shell quoting rules (`"$KMVAR_x"`, one variable per parameter, `#!/bin/bash -f` to stop globbing) rather than framing any of this as a security issue.

### Cited Findings

- Variables are exposed as env vars prefixed `KMVAR_`, with spaces turned into underscores ("File Name" becomes `$KMVAR_File_Name`). By default all variables are included; v11.0+ lets you choose none or specific ones. `ENV_`-prefixed variables set the unprefixed env var (for example `ENV_PATH` sets `PATH`). Scripts can read these variables but cannot change the KM originals. — [KM wiki, Execute a Shell Script](https://wiki.keyboardmaestro.com/action/Execute_a_Shell_Script)
- Quoting guidance from the same page:
  - Double-quote references (`cat "$KMVAR_File_Path"`).
  - Don't use single quotes, since bash won't expand inside them.
  - Use separate variables for separate parameters. Don't put quotes inside a variable, "because the shell has already processed quotes by the time it expands variables."
  - Globbing happens after expansion; disable it with `#!/bin/bash -f`.
  - Input can be chosen for stdin since v8.
  - The page has no security section.
  - Source: [KM wiki, Execute a Shell Script](https://wiki.keyboardmaestro.com/action/Execute_a_Shell_Script)
- A KM forum thread asks for an "options/arguments field" on Execute a Shell Script. That implies KM has no argv mechanism for inline scripts and env or stdin is the supported path. — [KM forum](https://forum.keyboardmaestro.com/t/suggestion-add-options-arguments-field-to-execute-a-shell-script/18772)

### Inferences

- Passing values as env vars has the same safety property as positional args: the shell expands `$KMVAR_x` as data and never parses it as code, provided the script quotes it. KM also exposes `%Variable%` text tokens in many actions. Whether those tokens are expanded inside the shell script text is not documented on the fetched page (see Gaps). If they are, that would be the injectable path.
- The `ENV_PATH` mechanism means a macro variable can change `PATH` for the script, which affects which binary a bare name resolves to. bnto's `env` option on shell-command carries the same risk.

### Gaps

- I could not confirm whether KM processes `%Variable%` tokens inside Execute Shell Script text. The fetched wiki page does not mention it.
- I could not find any Hammerspoon (`hs.task` takes an argument array) or BetterTouchTool documentation on argument passing or escaping within the tool-call budget. Not researched.

## Common lesson: do these tools pass values via argv/env/stdin by design, and do any prevent templating into the script body?

### Takeaway

Every peer that accepts a user-written script body offers an out-of-band channel for values: Automator and Shortcuts use stdin or `$@`, Alfred argv, Raycast `$1..$3`, Keyboard Maestro env vars and stdin. Alfred explicitly recommends argv over text substitution. Raycast is the only one structurally unable to template values into the script body. Home Assistant forbids templating the program name and drops the shell when templates are present, but re-splits rendered values, so argument injection remains. Node-RED is the negative example: its default concatenates the payload into a shell string with no warning. bnto's proposal (literal script, values only as positional args) matches the safest pattern among these peers and is stricter than HA.

### Cited Findings

- Alfred recommends argv "as you don't have to worry about correctly escaping the inputted query." — [Alfred Run Script](https://www.alfredapp.com/help/workflows/actions/run-script/)
- Automator offers "Pass input" as stdin or shell arguments. — [Apple Automator docs](https://developer.apple.com/library/mac/documentation/AppleApplications/Conceptual/AutomatorConcepts/Articles/ShellScriptActions.html)
- Raycast passes arguments positionally. — [Raycast ARGUMENTS.md](https://raw.githubusercontent.com/raycast/script-commands/master/documentation/ARGUMENTS.md)
- Keyboard Maestro uses `KMVAR_` env vars. — [KM wiki](https://wiki.keyboardmaestro.com/action/Execute_a_Shell_Script)
- HA uses exec without a shell when templated, plus `shlex.split`, and the program name is never templated. — [HA services.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/shell_command/services.py); [HA docs](https://raw.githubusercontent.com/home-assistant/home-assistant.io/current/source/_integrations/shell_command.markdown)
- Node-RED concatenates into a bash string in exec mode. — [90-exec.js](https://raw.githubusercontent.com/node-red/node-red/master/packages/node_modules/%40node-red/nodes/core/function/90-exec.js)
- Argument injection into a binary run without a shell can still be critical (HA ffmpeg). — [elttam](https://elttam.com/blog/your-house-has-an-ffmpeg-problem)

### Inferences

- Design recommendations for bnto:
  1. Keep the script literal and pass values via argv, as proposed. Consider env vars as a second channel, KM-style, for named values; `"$BNTO_FIELD_x"` reads better than `$3`.
  2. Make the mode explicit, not inferred from whether the content contains templates the way HA does it.
  3. Keep each templated value as exactly one argv element, with no re-splitting (bnto already beats HA here).
  4. In docs and examples, always quote (`"$1"`) and use `--` before positional data where the tool supports it. Literal scripts still pass `$1` into binaries that parse options or URLs (the ffmpeg lesson).
  5. Never fall back to a different shell per platform (the Node-RED Windows `shell: true` lesson).
- None of these tools ship a validator that rejects `{{...}}` inside the script body. bnto rejecting templates in the `sh -c` script at recipe-validation time would be stricter than every peer surveyed.

### Gaps

- Coverage of Hammerspoon, BetterTouchTool and the current Apple Shortcuts docs is incomplete (see the sections above).
- I found no formal CVE history for Alfred, Raycast, Keyboard Maestro or the Shortcuts shell actions themselves. This could mean their trust model (local user, own scripts) puts these out of scope for vulnerability reporting, but that is unconfirmed.
